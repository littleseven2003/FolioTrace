# 版本号与发布编排

## 四种编号，分别管理

| 对象 | 权威位置 | 编号方式 |
| --- | --- | --- |
| 软件版本 | package.json 的 version | SemVer：主版本.次版本.修订号，可带预发布后缀 |
| Git 提交 | Git 历史 | 每个完成且验证的小改动一个提交，不额外人工编号 |
| 项目数据协议 | schemas 与实际数据的 schemaVersion | 独立递增整数，当前 1 |
| 用户材料版本 | 业务 project.json 中 versionId | 稳定 ID＋可读标签，文件名保留时间戳；不使用软件版本号 |

开发文档随 Git 提交追踪，不给每份 Markdown 单独标 v1/v2。M0～M6 是开发阶段，不是发布版本。

## 当前与计划

当前 package.json=0.0.0：仅开发启动包，尚未发布桌面程序，不补造 v0.0.0 发布标签。当前协议版本仍是 1。

| 时期 | 软件版本 | 进入条件 |
| --- | --- | --- |
| M1～M5 内部试用 | 0.1.0-alpha.1、alpha.2… | 存在可运行的阶段构建且完成该构建验收 |
| M6 功能完整测试 | 0.1.0-beta.1、beta.2… | MVP 功能完整，主要做兼容和缺陷修复 |
| 发布候选 | 0.1.0-rc.1、rc.2… | 发布验收基本通过，仅修阻断问题 |
| 首个正式 MVP | 0.1.0 | M6 全部发布标准通过 |
| 兼容修复 | 0.1.1、0.1.2… | 修 bug、兼容性能改进，无破坏性数据变化 |
| 新功能迭代 | 0.2.0、0.3.0… | 一组对用户有价值的新功能 |
| 稳定版本 | 1.0.0 | 核心工作流、协议兼容策略和支持范围明确稳定 |

同一 alpha 阶段可以有多次版本，后缀按已发布顺序递增，不绑定 M 编号。不能因为完成 M2 就复用已经发布的 alpha.2。预发布后缀用数字自然递增，如 alpha.9 -> alpha.10。

## 升号原则

- 小改动 commit 后默认保持当前软件版本，记入 CHANGELOG 的 Unreleased。
- 只有明确准备一个测试构建或正式发布时才升号；一个发布可以包含多个小提交。
- docs、test、ci、chore 通常不单独触发应用版本升级；不要根据提交数量自动 +1。
- 0.x 阶段兼容修复升 PATCH；新功能或不兼容变更升 MINOR，并说明迁移。1.x 起破坏性变更升 MAJOR。不能以“未到 1.0”为由静默损坏旧项目。
- schemaVersion 独立于软件版本；只有结构/读取语义变化才升级并提供迁移、备份与测试。主题、布局、文档改动不升级 schemaVersion。
- 已发布版本和标签不可覆盖、删除重发；发现问题用新的 PATCH 或预发布编号。

## 发布检查表

1. 明确版本目标与发布内容，确认没有未提交的无关改动。
2. 更新 package.json；存在 package-lock.json 时同步根 package 与锁文件版本。不要新建第二份 VERSION 文件作为权威。
3. 将 Unreleased 条目整理到 `[版本] - YYYY-MM-DD`（Asia/Shanghai 日期），保留新的空 Unreleased 区域；写支持平台和迁移说明。
4. 完成 typecheck/lint/test/build 及当前阶段要求。构建产物展示的软件版本与 package.json 一致。
5. 独立提交 `release：准备发布 0.1.0 正式版` 或 `release：准备发布 0.1.0-alpha.1 测试版`；标题的描述以中文表意。
6. PR 合并并通过 main 的检查后，对确切提交创建 annotated tag `v<package.version>`。不要在未合并分支提前打正式标签。
7. 推送该标签，创建 GitHub Release。alpha/beta/rc 勾选 Pre-release；打包文件带版本与平台，如 FolioTrace-0.1.0-macos-arm64.dmg。
8. 核对远程标签目标、发布说明、安装包版本一致，再声明发布成功。软件签名未完成必须说明，不能宣称已签名。

命令示例（只在对应发布已验收且获授权时运行）：

```sh
git tag -a v0.1.0 -m "文脉 0.1.0 正式版"
git push origin v0.1.0
```

本次仅完善规范，不升级 0.0.0，不创建发布标签。
